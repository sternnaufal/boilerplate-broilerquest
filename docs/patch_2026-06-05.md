
## Bug Fixes & Improvements - 5 Juni 2026

### Unity MCP Package Update (v9.6.8 → v9.7.1)
- Updated `Packages/manifest.json` to pin `#v9.7.1` instead of `#main`
- Cleared old package cache and regenerated `packages-lock.json`
- No breaking protocol changes — all existing tools and `http://127.0.0.1:8080/mcp` endpoint remain compatible

### Fix: Singleton<T>.Awake destroyed wrong object
- **File:** `Assets/Script/Core/Singleton.cs`
- **Bug:** `Destroy(this)` destroyed only the component, leaving an orphaned GameObject with no Singleton component but potentially other components attached.
- **Fix:** Changed to `Destroy(gameObject)` to properly clean up the entire duplicate GameObject.

### Fix: LevelSelectController double-unlock bug
- **File:** `Assets/Script/Scene/LevelSelectController.cs`
- **Bug:** When a level was already unlocked but `SceneController.Instance` was null, `PlayBeginner()` and `PlayIntermediate()` would fall through and charge coins to unlock again.
- **Fix:** Added `return;` after the `SceneController.Instance == null` check when the level is already unlocked, preventing the fallthrough to `TryUnlockLevel()`.

### Improvement: FeedManager.TryConsumeFeed atomic method
- **File:** `Assets/Script/Managers/FeedManager.cs`
- **Why:** Multiple slots clicking simultaneously could race between `CanUseFeed(1)` and `UseFeed(1)`, consuming more feed than intended.
- **Fix:** Added `TryConsumeFeed(int amount)` — a single atomic check-and-consume method that returns false if insufficient.
- **Caller updated:** `Assets/Script/Gameplay/StarterKandangSlot/StarterKandangSlot.cs` — `OnPointerClick` now uses `TryConsumeFeed(1)` instead of separate `CanUseFeed` + `UseFeed` calls.

### Post-Patch Regression Fix: Starter gameplay buttons could not be clicked
- **File:** `Assets/Scenes/Starter.unity`
- **Related script:** `Assets/Script/Gameplay/StarterGameplayUI.cs`
- **Symptom:** Main menu buttons still worked, but after entering the `Starter` gameplay scene, gameplay UI buttons appeared visually normal yet did nothing. Affected controls included `PAUSE`, `HP`, `CLOSE`, `ShopButton`, `IoTButton`, and the Shop/IoT exit buttons.
- **Root cause:** `BQ_StarterCanvas` in `Starter.unity` was missing the `StarterGameplayUI` component. Raycasts and button `interactable` states were normal, but no gameplay UI controller existed to register runtime listeners through `ButtonHelper.AddListenerOnce(...)`.
- **Fix:** Re-added `StarterGameplayUI` to `BQ_StarterCanvas` and wired its serialized references to the existing scene objects:
  - `hudPanel` -> `BQ_HUD`
  - `pausePanel` -> `BQ_PausePanel`
  - `hpPanel` / `hpPanelRect` -> `BQ_HPPanel`
  - `pauseButton` -> `BQ_HUD/PAUSE`
  - `resumeButton` -> `BQ_PausePanel/RESUME`
  - `hpToggleButton` -> `BQ_HUD/HP`
  - `closeHpButton` -> `BQ_HPPanel/CLOSE`
  - `shopButton` / `iotButton` -> `BQ_HPPanel/ShopButton` and `BQ_HPPanel/IoTButton`
  - `shopAPK` / `iotAPK` -> `BQ_HPPanel/ShopAPK` and `BQ_HPPanel/IoTAPK`
  - `exitShopButton` / `exitIoTButton` -> each APK `ExitBut`
  - `coinText` -> `GlobalUIOverlay/Coin/CoinText`
  - `chickenShop` -> `BQ_HPPanel`
- **Lesson learned:** Compile-only verification was insufficient here. This was a scene wiring regression, not a C# compile error. Any change that touches Unity scenes, prefabs, package refreshes, or editor-generated YAML must be verified in Play Mode with actual UI interaction checks.
- **Verification:** In Play Mode on `Starter.unity`, synthetic UI clicks confirmed:
  - `ShopButton` opens `ShopAPK`
  - Shop exit closes `ShopAPK`
  - `IoTButton` opens `IoTAPK`
  - `PAUSE` changes state to `Paused` and sets `Time.timeScale = 0`
  - `RESUME` changes state back to `Playing` and sets `Time.timeScale = 1`
  - Unity Console showed 0 errors and 0 warnings
  - `StarterGameplayUI.cs` validation showed 0 errors and 0 warnings

### 🟢 Refactor Ideas (team discussion recommended)

| Idea | Rationale |
|------|-----------|
| **Split `StarterKandangSlot`** | Current 5 partial files are masking a 500+ line god class handling state machine, animation, IoT, bubble UI, wander AI, and minigame — 6 responsibilities. Split into separate `MonoBehaviour` components communicating via `UnityEvent`. |
| **Dependency injection / event bus** | Every class hard-couples to 4-6 singletons (`CoinManager.Instance`, `FeedManager.Instance`, etc.), making unit testing impossible. A lightweight event bus would decouple these. |
| **Null-safe singleton pattern** | The codebase universally uses `if (X.Instance != null) X.Instance.Y()` (two accesses). Switching to `X.Instance?.Y()` would reduce ~200 lines of null-check boilerplate across 15 files. |
